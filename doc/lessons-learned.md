# 判据与守则

跨主题的工程规则。格式与算法本身的不变量分别写在 [file-formats.md](file-formats.md)（容器/序列化）、[text-model.md](text-model.md) §6（文本回写）、[hxv4.md](hxv4.md) §6（加密层）里；本文只收**做任何一步都要先满足的判据**。

## 1. 改写工具的验收闸：零改动往返必须逐字节一致

- **判据**：不做任何修改地重建，PSB body 与原始**逐字节相同**
- **原因**：这条一旦成立，后续所有改写差异都只可能来自"你改的那部分"，排错范围立刻收敛
- **做法**：`tool/psb.py::rebuild({})`；`.scn` 层允许 zlib 压缩流不同（解压后比对 body）

## 2. 脚本的身份来自内容，不来自文件名

- **判据**：加密归档解出来的文件没有真名（伪名/哈希名），身份只能取 PSB 的 `root["name"]`
- **做法**：解析入口按**魔术字节**分类（`mdf\0` / `PSB\0`），并跳过没有 `scenes` 的 PSB（`.pimg` 之类也以 `PSB\0` 开头）

## 3. 同名副本按归档优先级取舍，且必须比对内容

- **判据**：krkrz 后注册者优先（本作 `patch > data`；FHD 项目是 `patch > data_fhd > data`）
- **做法**：按容器排序取最后一份；同内容视为重复副本，**不同内容视为覆盖** ——两者都要在索引里留痕（`_index.json` 的 `duplicate_copies`），不能静默丢

## 4. 长度字段按目标版口径重算，同一批产物不混用

- **判据**：同一批文件里出现两种口径 ⇒ 一定有一半是错的（详见 [text-model.md](text-model.md) §3）
- **做法**：单一函数 `tool/scn.py::page_length()`，校验脚本对两种口径分别计数

## 5. 参数类数据以运行态为准，静态派生值不作为判据

- **判据**：加密层参数（key / nonce / holder / context / lanes）由运行时算出；静态派生可能给出"能骗过部分校验"的错误值（[hxv4.md](hxv4.md) §5）
- **做法**：从运行中的进程读一次 → 落成 profile → 用**独立路径**（游戏内解包）比对产物

## 6. 验证判据要独立于被测实现

- **判据**：自写实现与"工具自产自销"的一致性证明不了正确性
- **做法**：① 密码学原语用公开测试向量；② 离线解包结果与另一条独立路径（游戏内注入式解包）逐字节比对；③ 取样覆盖：小文件全部、大文件抽查

## 7. 解析器遇到不认识的东西要报错，不要静默跳过

- **判据**：静默跳过会把"格式假设错了"伪装成"这类文件不存在"
- **做法**：未知类型/长度不符/校验失败 → 抛异常并带文件名与偏移；确需跳过时（如 `.pimg`）要显式记录原因并计数

## 8. 代码级：哨兵不要用 `None`，遍历不要靠递归

- **判据**：对象图里本来就有大量真 `None`（PSB 的 `null`），把 `None` 当"从根开始"的哨兵会让遍历从根重启、无限递归
- **做法**：独立哨兵对象 + 显式栈；实测这类数据嵌套深度只有十几层，"递归太深"通常不是真因

## 9. 中间产物与临时文件的去向

- **判据**：解包/提取的中间结果体积大且可由脚本重建
- **做法**：只把**文本与参数**这类小而不可再生的结果放进 `resource/`；解包产物、调试脚本、日志一律放 `tmp/`（`tmp/` 不入库），任务结束清空

## 10. 维度过滤器的判据：产物里必须能读出该维度

- **判据**：凡是用 `--domain` / `--lang` 这类参数缩小取数范围的工具，产物索引里必须记下**实际取到的维度值**，且该值要与参考真值比对过一次；过滤器只能“缩小”不能“静默失效”
- **失效形态**：`script/extract_text.py::split_container()` 若对 `*.xp3` 输入返回空的 domain（丢掉 `iter_scn_from_xp3()` 拼出的 `<domain>/<filehash>` 前缀），`--domain` 会静默失效，同名脚本的多域副本按「最后一份胜出」取到任意域——表现为自标简中、实为繁中，而产物索引的 `domain` 字段全为空串且无人报错
- **做法**：① domain 从 arcname 解出并**在解密前**过滤（既正确又快，单次全量提取从十几分钟降到几十秒）；② `_index.json` 写 `domains` 计数；③ 请求的域一个脚本都没取到时**直接报错退出**；④ 用另一条独立路径（游戏内明文解包产物）逐条比对，自标维度与实际维度必须一致
- 教训泛化：**过滤器失效比过滤器报错更贵**——它会产出看起来完全正常、但维度错了的数据集

## 11. 文档纪律

- 结论写进**对应主题的文档**，不另建"总结/汇总"文档（同一结论只允许存在一处）
- 只写当前成立的结论，不写探索过程与试错史；跨作不确定的结论标注 **【跨作需重验】**
- 每条结论都要能追到一个判据（可复跑的命令、可对照的文件指针、或另一条独立路径的验证）
- **一个逻辑行整行输出**，不按宽度硬折行（整理属一次性动作，不留在 `script/`）
- 明细/统计类的**机械输出不放进 `doc/`**：结论写文档，明细按需生成到 `tmp/`

## 12. 零改动往返是必要闸，不是充分闸

- **判据**：改写器必须能「不改任何内容地重建 ⇒ 逐字节相同」，但这条**只覆盖偏移量为 0 的情形**
- **反面实例**：`psb.rebuild()` 把 `offset_entries` 和字符串表一起平移了（它指向字符串表之前的对象图区），零改动往返全绿；一旦字符串变长/变短，重建出的文件立刻解析崩
- **做法**：再加一条**扰动闸**——任取一条字符串变长与变短各重建一次，要求产物能**重新解析**且字符串池内容与预期一致。只要新槽/新字符串真的写进去了，任何偏移量错误都会立刻暴露
- 同理可用于整数/引用改写：扰动后回读，比对「该字段变了、其余字段没变」

## 13. PSB 对象图是 DAG，不是树

- **判据**：同一个子对象可以被多个父节点引用（官方序列化器会去重完全相同的数组/对象）
- **后果**：① 遍历会重复访问同一位置（统计引用数必须**按位置去重**，否则「共享槽」判定全错）；② 两个 `row` 可能**共用同一个页列表**，此时它们的文本/`length` 物理上不可分离，除非做对象图手术（新增页数组 + 改父数组）——本项目选择按多数票写入并记录清单
- **实测**：FHD 项目 52,133 页里 13 页受此限制（另有 3 页受引用字节宽度限制）；本作 23,245 页里 3 页受页对象共享限制、4 页受引用宽度限制。逐条清单由 `script/writeback.py apply` 写入 `tmp/_report_apply.json`（`page_list_shared_conflicts` / `ref_width_skipped`），`script/verify_patch.py` 据此区分“已知限制”与“意外错写”

## 14. 定位"补丁不生效"：先分清"没被加载"与"加载了但被压住"

- **一次只改一个变量**：照抄官方条目时若 `segm` 字段偏移读错，会表现为 `Read error`，极易被误判成"canary 被引擎读到 ⇒ 域判别成功"。字段偏移错误必须先排除，再谈机制。
- **`Read error` 有两层含义**：它证明「该归档确实被读到」，但不证明「你插入的那条被查到」。要用**正确字段 + 正确尺寸**的探针（显示标记或落日志）才谈判定。
- **"没弹窗" ≠ "没执行"**：`System.inform` 在被 `try/catch` 包住、或有模态窗口干扰时可能看不到；优先用**标题栏 / 落盘文件 / 直接可见的文本变化**做信号，并给信号编号（如 `[RT-A-1]` 里的计数）以便区分"执行了几次"。
- **优先级链条里，同一批代码内的先后也是顺序**：`data/<lang>/scn/`(松散) 早于`<arc>><lang>/scn/`(归档内前缀)，所以松散文件永远输给归档；判断"文件放对没"之前先确认"排在哪"。
- **名字大小写会被规范化**（引擎哈希前转小写）。用大写名注册的条目永远查不到，而官方里"查不到"的文件可能只是因为大小写不同（`Storages.tjs` vs `storages.tjs`）。
- **影子替换官方脚本前先确认它被加载几次、每次解析到哪个域**：`default.tjs` 早（`main/`）+ 晚（`cn/main/`）两次，是不同的文件；影子只影响你覆盖的那一次。
- **钩子要幂等**：`addContinuousHandler` / 全局守卫 / `try{}catch{}` 三件套；失败只应"不生效"，不应让游戏起不来。
- **最小暴露面**：注册 autopath 时优先用带目录前缀的形式（`CN.xp3>cn/scn/`），它只影响该命名空间；用归档根（`CN.xp3>`）会插手**所有**裸名解析，风险面大得多。

## 15. 性能：先量再优化；热点是纯 Python 反序列化，只有多进程有效

- **实测分布**（FHD 项目 199 脚本 / 53,218 页；本作 102 脚本 / 23,245 页的实测见下条）：打包加密只要 2.7 s，`fetch`/`apply`/自检各 60–220 s，几乎全是 `tool/psb.py` 的递归反序列化（单脚本约 0.32 s、53k 页）。
- **线程无用**：PSB 解析与字符串处理都在 GIL 下；`zlib` 才释放 GIL。要并行就按**脚本**切进程。
- **陷阱：worker 里装全量数据**。`apply` 原本每个 worker 都 `load_text_maps()` 一遍（25+18+24 MB × N），8 进程跑 65 s、加到 16 进程只降到 55 s，看起来"并行没用"，实际是 I/O/解析被重复做了 N 份。改成"每个 worker 只读自己那个脚本的分片文件"后才随核数下降。
- **拆分是并行的前提**：一脚本一文件让 worker 的工作量与脚本大小成正比；用 `concurrent.futures.ProcessPoolExecutor` + 分块（`len(tasks)/(jobs*4)`）即可，注意**输出顺序/合并顺序必须固定**（本作按归档优先级顺序合并 fetch 结果）。
- **并行化不改语义的验收判据**：同一输入下产物 MD5 必须与串行一致（本作 `releases/CN.xp3` = `4e792bd3034837b6ae8c6b676457e223`）。
- **本作实测**：`fetch` 25 s、`apply` 39 s、`pack_patch` 15 s、`verify_patch` 约 20 s；清空 `tmp/` 后全链重跑 84 s，产物 md5 不变（`4e792bd3034837b6ae8c6b676457e223`）。

## 16. 多层转义会把反斜杠与 NUL 提前解释掉

- bash heredoc → Python 字符串 → 目标语言，三层转义叠加时极易把 \\（行连接符）与 \x00（NUL）提前求值，典型后果：Markdown 的行连接符被吃掉、`.py` 源码里混入真正的 NUL 字节（编辑器显示 `Binary file matches`、解释器报 `source code cannot contain null bytes`）。
- 规则：**这类内容用编辑工具直接写**，不要用 heredoc 拼接；写入后自查文件里 NUL 的个数（应为 0），`doc/` 下的 Markdown 必须是纯文本。
## 17. "Steam 版内容不全" 先查归档清单，再谈裁剪与差异

- **现象**：只读 `data.xp3` 时，本作只有 40 脚本 / 10,496 行，且与民汉是"严格子序列"关系（23 个脚本共 858 行"民汉有、Steam 无"），看起来像"官方做过全年龄裁剪"。三个语言域行数完全一致，更像是**构建级裁剪**。
- **根因**：游戏安装目录里还有官方 `patch.xp3`（1.10 GB）。它覆盖 40 条同名脚本并补上 62 条 ⇒ 完整版 102 脚本 / 23,245 行，与民汉**零差异**。
- **守则**：
  1. 提文本前先列**全部** `*.xp3` 的条目数与域直方图（`entries` / 每个 `domain` 的计数），确认哪个包承载剧本；本作 `data_sana.xp3` / `patch2.xp3` 都不含剧本。
  2. 见到"子序列 + 无替换/换序"的差异，先怀疑**自己少读了一个归档**，不要直接下"官方裁剪"的结论。
  3. 多归档要按**注册优先级**顺序传入（本作 `data.xp3` → `patch.xp3`，后者胜），并核对 `_index.json` 的 `overridden` 计数。

## 18. Hxv4 参数先试复用，再谈重抓

- 同系列两个发行体（本篇 / SANA EDITION）的 exe 不同（4,551,896 vs 4,583,128 B），但 Hxv4 参数**完全相同**：直接用姊妹项目的 `profile_live.json` 就能解开本作全部归档（映射表 Poly1305 通过 + 内容过滤器正确）。
- **守则**：拿到新构建先做一次性判据测试——`Hxv4Archive(path, profile)` 能建起来（tag 通过）**且** `read_entry()` 解出的头部是 `PNG`/`OggS`/`PSB`/`BOM`。两条都过就不用启动调试器；任一条不过才按 [hxv4.md](hxv4.md) §5 重抓。
- 反例仍然成立：**日文原版（非 Steam）打不开**，不要因为"同系列能复用"就以为参数是跨发行商通用的。

## 19. 原位改写的三个硬限：引用宽度、槽去重、页对象共享

- **引用宽度**：页里的文本引用是**定宽内联整数**（`STRING_Nx`，宽度 ∈ {1,2,4}）。要追加新槽就必须让新下标落进原宽度：本作 4 页的宽度是 1 字节（≤255），而新槽号 306/307 放不下 ⇒ 只能保留官方译文。想绕过要么复用已有同文槽，要么写完整序列化器。
- **槽去重**：官方脚本把相同文本去重成一个槽，于是一个槽被多页共用；这些页要写不同译文时必须**追加新槽 + 原位改引用**（本作 292 次重指、147 个新槽）。
- **页对象共享**：比槽共享更狠——官方把整个**页数组**去重成同一个对象，两行就连 `length` 槽都共用，**物理上不可分离**（本作 3 页受影响，写入多数票译文）。
- **守则**：`apply` 必须把这三类逐条写进报告（本作 `tmp/_report_apply.json`），且**独立的复核脚本要能区分"已知限制"与"意外错写"**（`script/verify_patch.py`：先按报告放行已知项，剩下的任何差异都算失败）。

## 20. 回写统计不能直接当验收结论

- `select_written=9` 看着像"漏了 2 个选项"，实际是 11 个选项里有 2 个两侧文本相同（`是`/`否`），根本没触发改写。
- **守则**：统计项只用于定位问题，验收要用"从 `resource/` 重建期望、逐页逐项比对产物"的独立脚本；计数类指标（"改写 N 次"）与目标类指标（"每个目标都达成"）必须分开，不能互相代替。

## 21. 文本"错位"先判方向，勿默认民汉错；音频时长是可复现的判据

全量语义校对在 `seアフター_01` row 29–37 发现两侧文本错位一格。第一反应是"民汉跨行改编"，
但音频证据把方向反转了：从 `patch2.xp3` 解出语音（`tmp/voice_check/`）测时长，
`sn7562`=6.40s 与民汉@30 的长句吻合、官方@30 的短句只有 ≈1.5s，逐行全是这个模式；
再用原始 PSB 双向对照确认两侧语音挂载逐行相同、文本错位仅在官方侧——
官方中文把一句无语音旁白拆成两行并整体下移，还漏译了 JP@37。

**守则**：校对发现两侧文本对不上时，先用"该行音频时长 vs 两侧文本朗读长度"判别哪一侧偏离日文原文，
再决定修补方向；位置映射的最终依据是行内音频归属，不是 pairs 的行号配对本身。
另：本作语音不在 `voice.xp3` 而在 `patch2.xp3`，条目名哈希 `<voiceid>.ogg`（`doc/hxv4.md` §8）。
